# SOLID

Reference: Robert C. Martin, SOLID Principles.

## Interpretation

Apply SOLID pragmatically.

## SRP

A class should have a single reason to change.

A responsibility represents a cohesive business or technical concern.

A class may contain multiple methods provided they evolve for the same reason.

Do not fragment cohesive behavior into dozens of microscopic classes.

## OCP

Extend behavior when necessary.

Do not introduce extension points prematurely.

## LSP

Derived types must preserve expected behavior.

## ISP

Expose interfaces tailored to consumers.

Avoid fat interfaces.

## DIP

Depend on abstractions only when they provide architectural value.

Avoid interfaces with a single implementation unless there is a clear architectural reason.

## Never

Do not apply SOLID mechanically.
